# JUST-RAG SSE completion: how and why

English translation of the original read-only investigation. References and conclusions describe the inspected version, not a new execution during translation. Original wording remains in Git history.

The investigation is complete. Browser chat completion in JUST-RAG has two layers: `streamChat()` requires `done` for the same Run, network EOF, and parsed trailing data. The chat reducer requires `final.response` followed by `done` before marking the message `complete`. `done` ends the protocol; it does not itself mean business success. `error → done` is still failure.

These are static source findings, not runtime verification. The project HEAD was `efb58712923a43e523d4e4184c509c12289dfd71`, and `git status --porcelain` was empty before and after investigation.

For a user sending a question, the actual chain is:

1. Browser `App.tsx:235–255` creates an assistant message and `AbortController`, calls `streamChat`, and forwards the Run ID and events to the reducer. `client.ts:111–123` sends POST `/api/v1/chat/stream` and reads `X-Chat-Run-ID`, failing if it is absent. Server registration is in `bootstrap/application.py:237`, with the route's `/chat` prefix in `routers/chat.py:25`. The container actually injects `ChatAnswerService` and `ChatAnswerGenerator` at `bootstrap/application.py:190–194`.
2. The HTTP route at `routers/chat.py:91–104` generates a UUID, passes the same `run_id` to the application service, and encodes its events as SSE. `sse.py:21` emits `event: …\ndata: …\n\n`. The ordinary service path sends phase status and preview fragments, validates the final model structure, records the result, then emits `final → status(complete) → done` (`application/chat/service.py:182–225`). Without answerable evidence, it directly emits `final(insufficient_evidence) → done` at lines 174–180. That is still a completed, controlled business response.
3. Browser `sse.ts:9–14` combines the previous tail with current text and splits complete events on blank lines. Network chunks are not events; an event may span reads. `client.ts:124–154` keeps a decoder, buffer, and sawDone in memory. Every parsed event must match the response-header Run ID, and a parsed event after done throws. Even after done, it continues `reader.read()` until network EOF, then flushes the decoder and consumes the tail. If sawDone is still false, it throws an error meaning the chat stream did not finish completely.
4. The reducer separately holds the assistant's runId, response, status, and fragment index in memory. At `chatReducer.ts:121–137`, final replaces content with the final body and clears previews. On done, missing response means failure; only an existing response allows complete. `status(complete)` is a phase hint and cannot replace done (`76–84`). Events for a failed/complete message or a different Run are ignored (`69–75`).

One timing distinction is easy to miss: the reducer can mark a message complete during the done callback while the `streamChat()` Promise still awaits EOF. If an extra event or read failure follows, `App.tsx:256–265` dispatches fail and clears the active-stream flag in finally. When final already exists, the failure patch preserves the trusted body while marking failure; otherwise it clears body and previews (`chatReducer.ts:140–148`). A previously observed complete state therefore does not prove the entire network stream was validated.

| Received sequence | Current source behavior |
|---|---|
| final → done → EOF | The stream function can return successfully, and a message not already failed completes |
| final → EOF without done | The stream function throws incomplete-stream failure; the message fails but retains the final body |
| done → EOF without final | The stream function can return successfully; the message fails with an incomplete-answer message |
| error → done → EOF | The protocol ends normally; the message remains failed |
| final → done → another parseable event | The stream function throws for data after termination; App marks failure again |
| Different Run ID | The stream function rejects the event; the reducer independently checks isolation |

Cancellation at `App.tsx:301–307` aborts fetch, explicitly marks cancellation, and clears the generating flag. `streamChat` has no reader.cancel/releaseLock finally of its own. This investigation did not verify how server disconnect cancellation reaches the model Provider, so it cannot establish that cancellation always terminates all backend work.

Historical evidence and inference must remain separate:

- **Direct: trusted final results are separate from previews.** Archived design `docs/archive/specs/2026-04-27-token-level-streaming-design.md:45–47,70–79` explicitly aims to avoid treating generated previews as completed answers and preserves citation validation: preview first, final only after complete JSON and citation validation, and error/done with discarded previews on failure. Current `service.py:185–200,211–225` and the reducer's final replacement preserve that constraint. The earlier `2026-04-27-chat-stream-and-web-design.md:69–71` sliced only after complete validation, explicitly prioritizing citation correctness. That earlier phase cannot establish that the current implementation lacks token previews.
- **Direct contract, inferred rationale: final and done have separate jobs.** Original SSE design `2026-04-27-chat-stream-and-web-design.md:177–178,200–209,256–257` states that final carries structured results/citations and closing without final or done fails. From this contract and current code, explicit done plausibly distinguishes expected protocol termination from premature disconnection, while final establishes a business result. No complete discussion of why a single event was rejected was found; this inference is not the author's own statement.
- **Supported: strict validation was added later, not by the recent comment commit.** Local `git log --follow`, `git blame -L 121,155`, and introducing-commit/parent comparisons show that `971d271` (2026-04-27) left the loop at EOF without sawDone. `ed41c061f061fe1da0906325f442165b141ea98e` (2026-08-05, `fix: enforce client stream and request identity`) introduced response-header Run ID, sawDone, rejection of post-termination events, and EOF-tail parsing. Its parent and diff were directly inspected. `3261c8e` later added Chinese explanatory comments; it did not originate these mechanisms. Current `client.test.ts:213–241` rejects Run ID mismatches and streams closed without done. Those tests were read, not executed in this investigation.
- **Inferred: the cost of waiting for EOF.** Reading to EOF checks for events after done, but also means the function keeps waiting if the peer sends done without closing. The function has no internal timeout. This follows from its loop; no simulation was run and no dedicated rationale for the tradeoff was found.

The phrase complete validation also needs qualification. `sse.ts:18–28` is not a complete SSE/schema validator: it extracts only `event: ` and `data: ` lines, ignores blocks missing either, and asserts the parsed JSON type directly. `client.ts:149–152` adds a blank-line delimiter to the EOF tail before parsing. It therefore rejects parseable events after done, not arbitrary extra raw bytes. It does not prove every trailing byte is valid or that every unknown event type is rejected. The ordinary-sequence conclusions above apply to the server's current event contract.

Future changes should preserve Run isolation, final's trusted-result role, done's termination role, failure remaining failure after done, and failure on EOF without done. Before returning immediately at done or allowing unknown events, decide whether post-termination violations must still be detected rather than simply deleting checks.
