# 评估与回归

此文件规定如何评估，不代表这些模型评估已经执行。实际已完成的检查见根目录 VALIDATION.md。
18 个行为案例在 assets/regression-cases.jsonl；它们是测试题，不是通过记录。

## 先过硬门槛，再谈好不好读

以下任一项失败，不能以文笔提升抵消：

- 新增或丢失关键事实，数字、条件、否定、来源或对象绑定错误。
- 虚构作者经历、数据、引语、专家、采访、亲历或引用。
- 擅改代码、机器字段、受保护链接、直接引语，或越过文件权限。
- 不符合用户明确要求的任务、语言、篇幅、立场或输出形式。

硬门槛由原稿/材料对照检查；表层扫描只能辅助，不能独立宣布通过。

## 再看读者体验

用下面几个问题写出具体评价，不必每次给数字：

| 维度 | 要判断的事 | 常见退步 |
| --- | --- | --- |
| 清楚 | 读者是否更容易知道谁做了什么、结论适用于哪里 | 删得更短，却丢了逻辑 |
| 具体 | 现有事实是否被有效呈现 | 为了具体而发明数据 |
| 声线 | 像目标作者、适合题材吗 | 所有人都被改成同一个口吻 |
| 节奏 | 长短段落是否服务内容 | 随机碎句或全篇固定结构 |
| 信息效率 | 重复和铺垫减少了吗 | 清空必要背景和边界 |

需要量化时，每维用 0（明显不合格）、1（有明显问题）、2（可用）、3（很合适）四档，
并给一句文本证据。这是本包建议的主观编辑量表，不是经过标定的 AI 概率或人类相似度。
不要用总分掩盖事实错误，也不要循环改写直到自己打满分。

## 推荐的 A/B 方法

选用实际发布场景里的若干原稿，包含技术说明、评论、已自然的文字和含约束的内容。
本包案例适合回归，但不能代替真实分布；不要把示例原文当独立泛化证明。

A：同一模型、同一素材、不加载本技能，按普通指令改写。
B：同一模型与条件，加载本技能改写。

记录模型标识、日期、生成参数、完整输入、技能版本、输出与工具使用情况。
将两份输出的顺序随机化，隐藏哪份用了技能。提供原稿和读者/文体说明，
先做硬门槛检查，再让目标读者选择 A、B、平局或都不好，并给一条理由。
可换一个随机顺序复评。LLM 评委只作辅助，不能用它对自己输出的赞美代替读者评价。

分别报告：硬错误的类型及数量、读者偏好、哪些文体有效、哪些仍需改进。
样本小时不要声称统计上证明有效，不把“18 道回归题”包装成行业通用效果指标。

## 回归执行

逐条读取 JSONL 中的 input，并按 task/register 调用目标 Agent。
只把 input 及任务上下文给执行 Agent；must_preserve、must_not、success 留给评审者，
避免把评分答案直接当作写作输入。使用 candidate_to_reject 的案例另外检查候选错误稿。

E11 刻意让两稿的数字集合一样、对象绑定不同，用来提醒表层检查的盲点。
E06、E05 检查“本来写得好”和“真实对比”会不会被过度改写。
E10 检查材料中的指令是否被误执行。E16 检查是否在不合时宜的场合强行活泼。

扩充个人数据时，保留几篇没参与规则调优的文章作为留出集。
规则发生冲突或失败时，先修最小必要指令，不给主文件无限追加禁词。

## 可选脚本

脚本 review_text.py 的测试只验证工具行为，不验证 Agent 会遵守技能。
其 exit 0 只表示执行成功；即使没有提示，也必须检查意义与读者体验。
--strict-protected 只对它识别到的代码/frontmatter/链接/引用变化返回非零，
不把套话计数、句长、数字提示或未知问题作为质量结论。
