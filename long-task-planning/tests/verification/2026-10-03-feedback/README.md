## 怎么重跑

在仓库根目录运行，需要 Python 3.10 以上，只用标准库：

```bash
python3 -m unittest discover -s long-task-planning/tests -p 'test_*.py'
```

```bash
python3 -m unittest discover -s codex-orchestration/tests -p 'test_*.py'
```

记录证据时用同一套测试，输出成 JUnit XML 报告（多数测试工具都能输出的通用报告格式），这样 `longtask.py record --junit` 能读：

```bash
PYTHONDONTWRITEBYTECODE=1 python3 long-task-planning/tests/junit_report.py --start long-task-planning/tests --out <报告路径>.xml
```

变异检查（故意把代码改坏，看测试能不能发现）：

```bash
python3 long-task-planning/tests/mutate.py
```

## 测试方法

- 每个行为改动先写测试，在旧代码上运行，确认失败的原因就是要修的问题，再改代码。失败日志按条目保存在 `local/red/`。
- S2-F20a 有两个测试在改代码前就通过：一个检查调换或删除已提交的行仍报错，一个检查 goal.md、plan.md 的记录部分不能插行。它们守的是不能放宽的现有行为。它们是否有效靠变异检查证明：把“行序”比较去掉、给 goal 和 plan 也放开插行，这几个变异都被它们发现。
- 每个新行为都配了变异，定义在 [mutate.py](../../mutate.py)。本轮从 131 个增加到 164 个。[test_mutate.py](../../test_mutate.py) 随整套测试一起跑，检查每个变异要替换的代码片段在目标文件里正好出现一次、引用的测试都存在。
- long-task-planning 的测试从 105 个增加到 121 个；codex-orchestration 有 9 个测试。每次提交前两套都完整跑过，并用 `record --junit` 记录，报告保存在 `local/reports/`。
- 环境：Mac，Python 3.14.7，git 2.47.1。仓库总校验 `scripts/validate_all.py` 通过 uv（Python 的包管理和运行工具）运行，用的是 Python 3.11.2，校验里会再跑一遍两套测试和 ruff（一个 Python 代码检查工具）。运行时设了 `UV_OFFLINE=1`，只用本机已有的 ruff 0.16.10 和 PyYAML，不下载。

## 真实项目试用

试用都是只读的：只在另一个真实项目里运行 `lint`、`check-brief` 这类只读命令，没有改那个项目的文件，也没有跑它的测试。原始输出在 `local/trial/`。

- **S2-F20，插行和行序**：那个项目里两个代理在同一工作区记证据。一方只提交了自己的几行，另一方的一行留在工作区，夹在已提交的行之间，旧版 `lint` 因此报“不是只追加”。后来有人手工把这一行挪到末尾再提交，绕过了报错。新版 `lint` 在那个项目上通过。它的 179 行证据里有 1 处行序和时间顺序相反：一条审核记录写在一条时间更晚的测试记录之后。那个条目只有这一次审核，所以按时间选和按行序选结果相同，没有出现判断错误。
- **S2-F19，简报的本批条目**：用新版 `check-brief` 检查那个项目最近 3 份简报。2 份通过，取出的本批条目和简报的本意一致（分别是 3 个和 2 个条目）。1 份被拒，因为其中一个条目在简报写好之后被决定不做；这符合新规则。
- **S2-F18，指纹范围**：在本轮任务自己的 items.json 里加 `fingerprint.include`。这个仓库放着多个 skill，加之前改别的 skill 也会让本轮的测试证据变旧。加上之后：
  1. 旧证据显示“记录时的指纹范围（看全部文件）和现在的设置（只看 …）不同，要在现在的设置下重跑”，没有再写“之后代码改过”跟一个空列表；
  2. 在新设置下重跑两套测试并记录后，S2-F18a 到 S2-F20b 五项显示“当前版本已验证”。

  最初只列了两个 skill 目录和 `.gitignore`。随后发现 `scripts/validate_all.py` 还读 `scripts/` 和 `skills.json`：不列它们，这两处改了也不会让仓库总校验的证据变旧。所以把它们也加进了 include。

## 过程中发现的问题

都已处理。第 1 条的三个问题改的是 skill 的行为，修之前都先写了会失败的测试；第 2 到 5 条只改测试、变异定义、提交方式或代码写法，不改 skill 的行为。

1. **FEEDBACK 没写到的三个问题**：核实时额外发现，已并入对应条目。
   - 给已有任务改 `fingerprint.exclude` 后，`status` 写“之后代码改过”，文件列表却是空的，读的人找不到原因。并入 S2-F18b。
   - `check-brief` 原来把全文任何位置出现的编号都当本批条目，没有本批列表的简报也能通过。并入 S2-F19。
   - evidence.jsonl 的“不是只追加”报错一旦提交，就会永久留在 git 历史里，以后每次 `lint` 都报；手工挪行绕过它，又会让“最近一次审核”取错。并入 S2-F20a、S2-F20b。
2. **变异检查的匹配文本过时**：S2-F18 把内部的 `excludes` 参数统一换成 `scope` 后，整套测试里的 `test_mutate` 报 3 个变异要替换的片段在代码里找不到了。改成新写法后 3 个变异都被测试发现。第一轮加的 `test_mutate` 在这里拦住了变异检查悄悄失效。
3. **另一个 skill 的测试用了旧的简报写法**：codex-orchestration 的 `test_codex_launch.py` 用的简报没有“范围”一节，S2-F19 之后被拒。这是这一轮批准的写法变化，所以测试里的简报改成模板的格式；检查“简报无效”的用例改成“范围里的编号不存在”。
4. **只暂存部分改动时文件权限变了**：提交 S2-F20 时只暂存了 longtask.py 的部分改动，手工写入暂存区的文件权限从可执行（100755）变成了普通文件（100644）。提交前比对 HEAD 发现，已改回 100755，提交里的权限没有变化。
5. **收尾时仓库总校验报了 2 处 ruff 问题**：每次提交前我只跑了两套测试，没有跑 ruff；仓库总校验在收尾时才跑 ruff。一处是本轮 S2-F19 的测试用 `"\n".join([...])` 拼固定文字（FLY002）；改成一个字符串常量，用脚本确认改前改后的文字逐字节相同。另一处是第一轮关闭后另一个会话的提交 `20b91bb` 里，`test_snapshot_matches_commit.py` 的 `subprocess.run` 没写 `check=False`（PLW1510）；补上后行为不变，因为默认值就是 False，同文件其他调用也都这样写。两处修好后两套测试重跑通过。

## 定时检查反馈的任务

按用户 2026-10-03 的要求，在 Claude 桌面应用里建了定时任务 `long-task-planning-feedback-watch`，每 6 小时检查一次 FEEDBACK 有没有新条目。任务只在本机桌面应用打开时运行，提示词只在维护者本机。它的做法：

- 条目是否处理完，只看 FEEDBACK 里这一条自己的正文：有以 `- 已处理：` 或 `- 不处理：` 开头的行，就算结束。
- 新条目先核实；确认的再出方案。
- 这个仓库里还有没关闭的长任务时，只核实、出方案，不改代码。已经写进某个未关闭任务的条目（items.json 里 `added.why` 写了它的 F 编号）整条跳过。
- 没有未关闭的任务时，按本轮的流程做：先写失败测试，再实现，然后跑变异检查、两套测试、仓库总校验，通过私人信息检查后提交并推送。

这个任务建好时处于停用状态，第一次预定的运行没有发生；10:00 已启用。它第一次实际运行的结果是条目 S2-R6 的证据，看 `status`。

## 没有验证的

- 只在 Mac 上跑过测试，Python 版本是 3.14.7 和 3.11.2；SKILL.md 承诺的最低版本 3.10 没有单独跑。Linux 和 Windows 这一轮没有测。
- `fingerprint --include` 在别的机器上算指纹的流程，只在测试里用临时仓库模拟过，没有在真实的另一台机器上跑。
- S2-F19 的新规则只在一个真实项目的 3 份简报上试过；标题写法不同的简报（例如“范围”不在标题里）会被拒，需要按模板改写。
- 定时任务能否在没人操作时完成全部步骤（例如中途遇到需要批准的工具调用），要等它真正运行一次才知道。
