## 怎么重跑

在仓库根目录运行，需要 Python 3.10 以上，只用标准库：

```bash
python3 -m unittest discover -s long-task-planning/tests -p 'test_*.py'
```

```bash
python3 -m unittest discover -s codex-orchestration/tests -p 'test_*.py'
```

记录证据时用的是同一套测试，只是输出成 JUnit XML 报告（多数测试工具都能输出的通用报告格式），这样 `longtask.py record --junit` 能读：

```bash
PYTHONDONTWRITEBYTECODE=1 python3 long-task-planning/tests/junit_report.py --start long-task-planning/tests --out <报告路径>.xml
```

变异检查（故意把代码改坏，看测试能不能发现）：

```bash
python3 long-task-planning/tests/mutate.py
```

只跑其中几个时把名字写在后面，例如 `python3 long-task-planning/tests/mutate.py "find-tests prefers the longest fragment"`；名字写错会报错，不会悄悄什么都不跑。

## 测试方法

- 每个行为改动都先写测试，在旧代码上运行确认失败，而且失败原因就是要修的问题，再改代码。失败日志按条目保存在 `local/red/`。
- 每个新行为都配了变异：把实现里的关键判断改坏，确认对应测试会失败。变异定义在 [mutate.py](../../mutate.py)，本轮结束时共 131 个。[test_mutate.py](../../test_mutate.py) 随完整测试一起跑，检查每个变异要替换的代码片段在目标文件里正好出现一次、引用的测试都存在，代码改了而变异没跟着改时马上能发现。全部变异的最终结果是条目 SK-R5 的证据，看 `status`。
- 每次提交前跑完整的 long-task-planning 测试并用 `record --junit` 记录，报告保存在 `local/reports/`。本轮最后一次代码改动后是 105 个测试；codex-orchestration 自己的 3 个测试也通过。
- 代码风格检查用 ruff（一个 Python 代码检查工具，用 uv 临时安装运行）：`uv run --with ruff ruff check long-task-planning/scripts long-task-planning/tests`。
- 环境：Mac，Python 3.14.7，git 2.47.1。

## 真实项目试用

在另一个真实项目的临时克隆上，用本仓库的新版脚本对照安装目录里的旧版脚本。克隆用 `git clone --shared` 建在临时目录，原仓库只读；试完已删除。原始输出在 `local/trial/`。

- **status 总数**：旧版显示的总数比条目数少 1（漏算了一个不做的条目），新版等于条目数。新旧版对每一项的判断完全一致。
- **status --brief**：37 行，完整输出 116 行。
- **lint**（检查任务文件格式和只能追加的规则）：通过。
- **钩子内容**：目标按日期显示。试用时发现问题行把用户的原话挤出了长度限制，已修，见[过程中发现的问题](#过程中发现的问题)。
- **find-tests**：在一份 2154 个测试的 Vitest（一个 JavaScript 测试框架）报告上运行约 1.7 秒。试用时发现对模板生成的标题挑错了片段，已修。
- **只改文档后的放宽**：在克隆的任务里加 `"test_exclude": ["docs/", "AGENTS.md"]` 后：
  1. 两项原来“旧版本验证过”的条目变回“当前版本已验证”，说明写的是“测试跑在某提交上，之后只改了测试不读的文件”；
  2. 再提交一次只改文档的改动，这两项不变；一项靠命令检查的条目变旧，这符合设计，因为命令检查不放宽；
  3. 再提交一次测试文件的改动，这两项变回“旧版本验证过”，绑定这个文件的审核也变旧。

## 过程中发现的问题

都已修好，修之前都先写了会失败的测试。

1. **变异检查脚本悄悄不跑**：传入不存在的变异名时什么都不跑，结尾仍打印“survived: []”，看起来像全部通过。现在会报错退出，结尾写明实际跑了几个（`118b983`）。
2. **只改文档的放宽从不生效**：放宽原来只认“记录里的提交内容正好等于记录时的指纹”。可 SKILL.md 推荐先记录、再把代码和证据一起提交，这时测过的内容在下一个提交里，放宽就不会生效。现在从记录里的提交往后找，第一个内容等于记录指纹的提交就是被测试的提交（`78aa973`）。
3. **问题行挤掉用户原话**：真实任务的钩子内容加上问题行后超过长度限制，只好少显示一条目标，用户自己的原话被挤掉。现在长度不够时先去掉所有问题行，再考虑少显示目标；改后同一份任务又显示回原来的目标数（`7af074f`）。
4. **find-tests 对模板标题挑出参数值**：像 `"allows %s -> %s"` 这样的参数化测试（同一段测试代码换不同参数跑多遍），标题原文不在源码里。原规则挑源码里能找到的最长一段，常常是参数值，例如 `running`。这个词在源码里出现在许多行，一条检查会同时套中不相干的测试，那个测试失败就会连累本条目。现在改成挑在源码里出现次数最少的一段，次数相同再挑最长的（`9706ecd`）。标题原文就在源码里时，它的出现次数不会多于它的任何一部分，所以仍然整句使用。为了评估，我从源码中解析出每个测试声明的标题模板，判断报告里每个测试来自哪个声明。按这个对照，同时套中多个测试声明的检查从 14 条降到 4 条。剩下的 4 条是参数值恰好也是另一个测试标题的开头，脚本会提醒“同时对应多个测试”。评估脚本和结果在 `local/trial/find-rules.*`。
5. **find-tests 没有匹配时无输出**：`--grep` 或 `--commit` 筛完一个测试都不剩时，什么都不输出，分不清是没有匹配还是脚本出错。现在在标准错误输出（stderr，和正常输出分开的提示通道）写一行提醒（`e4e11f2`）。
6. **公开仓库里写进了别的项目的名字**：一次提交的说明和审核备注写了另一个项目的名字。当时的私人信息检查用 `;` 连接，找到匹配也没有拦住提交。经用户同意，把这一个最新提交改写后强制推送，只改了那条备注和提交说明。之后每次提交前，私人信息检查都作为拦截条件放在 `git commit` 之前，同时检查暂存的文件、未跟踪的文件和提交说明。
7. **过时的变异要到最后才暴露**：最终的全部变异检查里有 4 个变异套不上当前代码：要替换的片段出现 0 次（代码改了写法），或者出现 2 次（别处复制了一行相同的代码）。mutate.py 把它们报为失败，没有放过，但之前每次改动只跑相关的几个变异，所以拖到最后才发现。现在 `test_mutate.py` 在每次完整测试时检查所有变异都能套用、引用的测试都存在。后一项也很重要：测试改名而变异没跟着改时，unittest 找不到测试也会失败退出，会被误判为“变异被发现”。
