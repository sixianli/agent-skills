# 重复错误记录

这份文件记录同一个错误第三次出现以后查到的原因，以及为它加上的硬性检查。硬性检查指每次都会运行、agent 跳不过去的东西，例如脚本里的检查或测试；只在说明里多写一句提醒不算。规则来自用户的全局说明：同一个错误第三次出现时，先停下，查清之前的预防为什么没起作用，加上硬性检查，证明它能拦住错误的重现，再把原因记在这里。

## 2026-10-24 CodeBuddy 工作者不照原样运行验收命令

**是什么错。** codebuddy-orchestration 这个 skill 把编码任务交给 CodeBuddy（腾讯的编程 agent 命令行工具），在那边做事的 agent 这里叫“工作者”。交给工作者的任务说明叫“简报”，其中 `## Acceptance` 一节列出验收命令，也就是证明改动做对了必须跑的命令，例如 `python3 -m unittest discover -s codebuddy-orchestration/tests -p test_cb_delegate.py`。工作者常把这些命令改写，例如在后面加上 `2>&1 | tail -40`（把错误输出并进普通输出，只看最后 40 行），或在前面加上 `cd <目录> &&`（先进入某个目录再运行）。CodeBuddy 的允许规则（列出工作者可以运行哪些命令的规则）从命令的第一个词起整条匹配，所以改写过的命令会被拒绝。被拒以后，工作者往往不再照原样运行，交回没验证过的代码。

**出现过几次。** 2026-10-22 到 10-24 的四个任务里出现过：免费模型 deepseek-v4.1-flash 一次，免费模型 hy3 三次。hy3 有两次被拒后就放弃，报告说运行命令的工具不能用，一个测试都没跑；审核方（指挥工作者、检查它交回的改动的 agent）只能自己补跑所有验收命令，以及“改动之前新测试应当失败”的检查。

**之前的预防为什么没起作用。** 工作者规则（`codebuddy-orchestration/templates/worker-rules.md`，每次启动工作者都附上的固定说明）从一开始就写了“照原样运行，不加 `cd`、管道、`&&`、`2>&1`”。第二次出现以后，又补了一句“改写过的命令被拒，就照原样再运行一次，这不算找绕路”，每份简报的 Constraints 一节也写了同样的话。这些都是写给模型看的提醒，模型照不照做，没有任何东西检查。被拒以后，旧规则里“被拒就不要找绕路”这句反而让它停下。提醒写得再长，模型照样可能忽略。

**加上的硬性检查。** `codebuddy-orchestration/scripts/cb-delegate.sh`（启动和续跑工作者的脚本）每跑完一轮，就把简报 `## Acceptance` 里的每条命令，和工作者这一轮实际发出的命令逐字比较。CodeBuddy 续跑（接着同一个对话再跑一轮）时常常把前几轮的命令也列在输出里（2026-10-24 查了三个任务，两个是这样，一个不是），所以比较时去掉上一轮已经出现过的调用，两种情况得到的结果相同。一条含换行的命令先合并成一行再比较，否则 `cd 目录` 换行 `python3 -m unittest …` 这样的一条调用会被拆开，第二行恰好等于验收命令，检查就被绕过了。有没照原样运行过的命令，报告里就打印一行 `!! acceptance command not run exactly as written in this round: <命令>`，脚本还会自动接着同一个对话续跑一次，告诉工作者照原样重跑哪几条，并说明被拒只表示改写的形式不允许、运行命令的工具仍然能用。照原样运行却被拒的命令算运行过，不触发续跑：那是允许规则没有放行，要审核方处理。这次自动续跑不占手动返工的次数上限（`CB_MAX_ROUNDS`）。自动续跑之后仍然没照原样运行，报告里的 `!!` 行还在，审核方据此自己跑验收命令。

**怎么证明它管用。** `codebuddy-orchestration/tests/test_cb_delegate.py` 用一个假的 CodeBuddy 程序输出事先写好的对话（参数写成真实输出里的形式：一段 JSON（一种用花括号和引号写的数据格式）文本）：输出改写过的命令时，脚本打印 `!!` 行并正好续跑一次；照原样运行（即使被拒）时不续跑；只出现在上一轮的命令不算这一轮运行过；含换行的命令不会被拆开骗过检查；自动续跑不占返工次数；只审核、不改代码的任务不做这项检查。2026-10-24 实测：把这批新测试放到加检查之前的 `cb-delegate.sh` 上，47 个测试里 4 个失败（`!!` 行和续跑、上一轮的调用不算、多行命令、自动续跑不占次数）；另外两个反向测试（照原样运行却被拒时不续跑、审核任务不检查）在旧脚本上本来就通过，改靠变异检查证明有用：故意改坏新脚本的 10 种写法（不过滤上一轮的调用、过滤得太狠、用子串匹配代替逐字相等、不合并多行命令、审核任务也检查、审核任务也续跑、续跑次数把自动续跑算进去、流水账 `ledger.jsonl` 不记 `auto` 标记、续跑时换新对话、去掉“续跑那一轮不再续跑”的守卫），每一种都至少让一个新测试失败；去掉守卫的那种会一轮接一轮无限续跑，测试以超时收场。
